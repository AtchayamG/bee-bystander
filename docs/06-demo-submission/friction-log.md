### Entry 1: Production Developer API Requires an Undocumented Private Root CA

* **Task attempted**: Connect a standard TypeScript HTTPS client to the production Bee developer API endpoint (`https://app-api-developer.ce.bee.amazon.dev/v1/me`).
* **Steps taken**: Followed the official API documentation at `https://docs.bee.computer/docs/proxy` and attempted standard Node.js `fetch()` and `https.request()` calls. Both fail immediately, before any HTTP status is exchanged. Reproduce with `node ops\probe-bee-live.mjs`, which sends no credentials:
  ```text
  GET https://app-api-developer.ce.bee.amazon.dev/v1/me  (no Authorization header sent)

    system trust store only (no custom CA)
      -> transport error: SELF_SIGNED_CERT_IN_CHAIN self-signed certificate in certificate chain
    PROD_ROOT_CA supplied
      -> HTTP 401  body: {"error":"unauthorized"}
  ```
  Both the `fetch()` (undici) and `https.request()` paths report the same code on Node v22.22.3. The exact OpenSSL code a developer sees depends on their runtime and trust store — `UNABLE_TO_VERIFY_LEAF_SIGNATURE` and `UNABLE_TO_GET_ISSUER_CERT_LOCALLY` are the other common shapes — but the outcome is the same: the connection dies before HTTP.

  Searched `docs.bee.computer` for "certificate", "CA", "TLS", or "SSL" — zero documentation exists regarding custom certificates. Only by cloning the official CLI repository (`https://github.com/bee-computer/bee-cli`) and inspecting `sources/certs.ts` did we discover an embedded PEM root certificate (`PROD_ROOT_CA`, CN=`BeeCertificateAuthority`, OU=`Trust and Privacy`).
* **Expected vs actual**: Expected a public developer REST API to terminate TLS with a publicly trusted Certificate Authority (e.g. Amazon Trust Services, DigiCert, Let's Encrypt). Instead, the production API relies on an internal private CA that fails in any standard runtime trust store unless explicitly configured via custom TLS agents.
* **Severity**: **High.** Any developer attempting to build a custom service, serverless backend, or web integration outside of the pre-packaged `@beeai/cli` binary will immediately hit a hard TLS failure with no explanation in the developer documentation.
* **Workaround**: Extracted `PROD_ROOT_CA` from `bee-cli/sources/certs.ts` into `services/bystander/src/certs.ts` and configured Node's `https.Agent({ ca: PROD_ROOT_CA })` on all client requests.
* **Suggested fix**: Either terminate developer API endpoints using Amazon Trust Services (which is pre-installed in standard OS and browser trust stores), or prominently document the private root CA requirement on `docs.bee.computer` with instructions for Node.js, Python, and curl.

### Entry 2: Transcript API Provides Flat Anonymous Cluster Labels Without Participant Attribution

* **Task attempted**: Enforce consent and attribute captures to specific participants (or differentiate between the device owner and third-party bystanders) using the transcript API.
* **Steps taken**: Inspected `/v1/conversations/:id/transcript` and `sources/resources/conversations/index.ts` in `@beeai/cli` v0.7.3. Utterances are typed as:
  ```typescript
  utterances: Array<{
    id: number;
    text: string;
    speaker: string; // e.g. "SPEAKER_0", "SPEAKER_1", or ""
    spoken_at: number | null;
  }>
  ```
  Searched the API and CLI for user profile mapping, voiceprint enrollment, contact linking, or a boolean flag indicating the wearer. None exist.
* **Expected vs actual**: For an always-listening ambient wearable designed to capture multi-party conversation, developers need to know *who* is speaking — or at least which cluster represents the wearer. The API returns only flat cluster strings generated by the acoustic diarisation model (`SPEAKER_0`, `SPEAKER_1`), without identity, role, or consent state.
* **Severity**: **High.** This is the defining architectural dilemma of ambient audio. Because the platform does not link clusters to identities, builders cannot implement consent or attribution without maintaining external mapping layers.
* **Workaround**: Bystander implements an explicit local **Speaker Consent Ledger** that maps anonymous acoustic cluster labels (`SPEAKER_0`, `SPEAKER_1`, `SPEAKER_2`) to enrolled participant profiles. Unmapped clusters default strictly to `UNKNOWN`, which triggers refusal under our safety invariants.
* **Suggested fix**: Introduce a speaker profile and enrollment endpoint in the Bee ecosystem (e.g. `/v1/speakers/enroll`), allowing users to label voice clusters or designate the primary wearer cluster from the mobile companion app.

### Entry 3: Conversations and Summaries Are Strictly Read-Only Upstream

* **Task attempted**: Redact sensitive bystander speech and delete unconsented conversations from the Bee cloud storage.
* **Steps taken**: Analyzed resource operations across the Bee CLI and API. Facts (`/v1/facts`) and Todos (`/v1/todos`) provide full CRUD (`GET`, `POST`, `PUT`, `DELETE`). However, Conversations (`/v1/conversations`) and Daily Summaries (`/v1/daily`) provide only `GET` endpoints.
* **Expected vs actual**: Expected privacy-conscious developers to be able to redact, edit, or purge unconsented captures from the user's timeline via `DELETE /v1/conversations/:id` or `PUT /v1/conversations/:id/transcript`. The API does not expose any mutation endpoints for conversations.
* **Severity**: **Medium.** A wearable that records third parties without consent needs an API mechanism to expunge or redact those records upon request. Because the API is read-only, redaction cannot be persisted back to the Bee cloud.
* **Workaround**: Bystander acts as an in-flight redaction proxy and MCP provider. Rather than mutating cloud storage, it intercepts data before downstream LLMs or assistants consume it, suppressing unconsented text and withholding summaries at the gateway layer.
* **Suggested fix**: Provide `DELETE /v1/conversations/:id` and `PUT /v1/conversations/:id/redact` endpoints so privacy-preserving middleware can permanently purge or sanitize captured audio and transcripts in the cloud.

### Entry 4: MCP Protocol Floor Default Sits Below Hackathon Specification Minimum

* **Task attempted**: Ensure the Bystander MCP server strictly satisfies the hackathon minimum protocol version of `2025-11-25`.
* **Steps taken**: Built against `@modelcontextprotocol/sdk` 1.30.0, which advertises `LATEST_PROTOCOL_VERSION = '2025-11-25'`, but sets `DEFAULT_NEGOTIATED_PROTOCOL_VERSION = '2025-03-26'` and supports versions down to `2024-10-07`. Probing with `ops/probe-protocol-version.mjs` revealed that a client requesting older versions was served those older versions by default.
* **Expected vs actual**: Expected the SDK to provide a `minProtocolVersion` option in `StreamableHTTPServerTransport`. In reality, the SDK has no floor configuration, meaning a server claiming `2025-11-25` will silently downgrade if an older client requests it.
* **Severity**: **Medium.** A developer claiming compliance with the 2025-11-25 spec floor in their hackathon submission may unwittingly serve 2024 or early 2025 protocol dialects to judges and clients.
* **Workaround**: Implemented request body rewriting during the `initialize` handshake in `services/bystander/src/server.ts`, raising any sub-floor `protocolVersion` to `2025-11-25`. Verified via `ops/probe-protocol-version.mjs`.
* **Suggested fix**: Add a `minProtocolVersion` parameter to `StreamableHTTPServerTransportOptions` in the MCP TypeScript SDK to let servers reject or upgrade sub-floor clients cleanly.
